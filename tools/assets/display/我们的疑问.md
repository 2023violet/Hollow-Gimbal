# Themis 字体与图片资源正式方案

## 1. 背景

当前 `tools/assets/display/` 目录里同时混有几类内容：

- 历史项目直接使用的字模数组
- 图标数组
- 与旧平台耦合的头文件
- 重复定义和命名不统一的遗留数据

这说明旧资产有参考价值，但已经不适合直接作为 Themis 当前工程的正式运行时方案。

这次重构的目标不是“把旧数组换个地方放”，而是建立一套能够长期演进的资源体系：

- 支持多字体共存
- 支持多图片搭配
- 支持 BMP 原始稿长期归档
- 支持工具导出结果回溯
- 支持应用层正式编译资源
- 支持未来脚本化自动生成

## 2. 参考思路

### 2.1 Zephyr

Zephyr 在字符帧缓冲样例中，倾向于把字体资源作为编译期静态资源处理，由显示子系统在运行时直接消费，重点是“契约稳定、格式明确、尽量少做运行时动态管理”。

对 Themis 的启发：

- 字体与图片优先在编译期集成
- 运行时不依赖文件系统临时解析资源
- 驱动层只关心显示格式，不持有业务资源所有权

### 2.2 RT-Thread

RT-Thread 的内核层本身并不主张把 GUI 资源体系直接塞进内核，而是更强调组件、软件包、GUI 中间件和应用层之间的职责分离。

对 Themis 的启发：

- 不要把字库和图片塞进 BSP 或驱动层
- 组件层只提供绘制 ABI
- 资源数据应归属于应用层

### 2.3 ESP-IDF / Espressif 生态

Espressif 的显示方案经常允许两类资源并存：

- 一类是直接编译进固件的静态资源
- 一类是放在文件系统、分区或外部存储中的资源

对 Themis 的启发：

- `tools/assets/display/` 可以作为源资产与设计归档区
- `applications/resources/` 作为正式固件资源区
- 两者长期并存，而不是二选一

## 3. Themis 当前存在的问题

### 3.1 旧根目录 `font/*.c` 不是正式运行时入口

现状上，这些文件并没有进入当前显示服务的正式调用链，且内部存在：

- 平台头文件耦合
- 命名历史包袱
- 重复数组定义
- 图标和字体混放

所以它们更适合作为历史资产档案，而不是未来的正式运行时接口。

### 3.2 当前显示服务是硬编码演示

当前显示逻辑只是在 `display_service` 里手写了小字模，展示单纯字符串轮播。

问题在于：

- 不支持多字体
- 不支持图片组合
- 不具备资源复用能力
- 无法形成正式的页面搭配范式

### 3.3 工具导出格式和运行时格式混淆

像下面这样的导出：

```c
0x28, 0x18, 0x05
```

它们通常不是图像内容本身，而是导出工具附带的辅助信息：

- 宽度
- 高度
- 每行字节数

这部分应该进入运行时资源描述结构，而不应该混进正式像素数据里。

## 4. 总体设计目标

Themis 正式资源方案要同时满足以下目标：

1. 支持多字体、多图片、多页面布局共存。
2. 支持字体与图片的统一资源描述方式。
3. 支持常见导出工具格式接入。
4. 优先适配 SSD1316/SSD1306 页式显存格式，减少运行时转换成本。
5. 保留源资产与工具原稿，方便后续微调与追溯。
6. 保持组件层纯净，应用层拥有资源数据所有权。

## 5. 分层与目录策略

### 5.1 `tools/assets/display/` 的定位

`tools/assets/display/` 是源资产工作区，不参与正式编译。

它保存：

- 原始 BMP
- 工具导出原稿
- 历史数组档案
- 资源设计文档

### 5.2 `applications/resources/` 的定位

`applications/resources/` 是正式运行时资源区，参与固件构建。

建议结构：

```text
applications/resources/
|-- display_assets.h
|-- fonts/
|-- images/
`-- README.md
```

### 5.3 `components/display/mono_canvas/` 的定位

组件层只负责：

- 资源 ABI
- 位图格式定义
- 文本/图片绘制能力
- 文本测量与布局基础能力

组件层不负责：

- 具体字体内容
- 具体图标内容
- 业务页面资源

## 6. 正式运行时资源契约

Themis 正式运行时资源统一通过 `mono_canvas` 相关资源结构进行描述。

建议包含以下概念：

### 6.1 位图格式

- `MONO_BITMAP_FORMAT_PAGE_VLSB`
  说明：按页存储，纵向 8 点打包，最低位对应页内顶部像素。最适合 SSD1316/SSD1306。
- `MONO_BITMAP_FORMAT_ROW_MSB`
  说明：横向逐行取模，最高位优先。兼容大量字模软件的常见输出。

### 6.2 图片资源

图片资源至少需要描述：

- 宽度
- 高度
- 步进 `stride`
- 像素格式
- 纯像素数据指针
- 数据长度

### 6.3 字体资源

字体资源至少需要描述：

- 行高
- 基线
- 默认字距
- glyph 列表
- 回退字符
- glyph 对应的像素数据 blob
- glyph 的位图格式

这样做的好处是：

- 字体不必强制等宽
- 可以只保存必要字符
- 未来能扩展到 UTF-8/中文
- 图片和字体都能复用同一套位图解码逻辑

## 7. 页面搭配策略

Themis 的显示页面不应退化成“只显示一张大图”或“只显示一种字体”。

建议至少支持以下组合范式：

### 7.1 状态页

- 左侧图标
- 中上标题
- 中下副标题
- 右下状态数字或版本号

### 7.2 参数页

- 参数名使用较小字体
- 参数值使用较大字体
- 单位使用独立字体或缩小字体

### 7.3 引导页 / Logo 页

- 图片主视觉
- 一行标题
- 一行版本或状态说明

## 8. 字体与图片如何共存

### 8.1 字体适合表达“可变内容”

例如：

- 温度
- 时间
- 状态文本
- 参数值

### 8.2 图片适合表达“固定语义”

例如：

- 加热图标
- 制冷图标
- 泵图标
- 警告图标
- 品牌 Logo

### 8.3 不建议的做法

- 用整张大图去承载所有页面内容
- 把每一句固定文本都做成图片
- 一个页面只依赖单一字体或单一图片

正确做法是：

- 固定语义用图标
- 变化内容用字体
- 版式用页面逻辑组织

## 9. 工具导出数据的解释

### 9.1 为什么会多出 `0x28, 0x18, 0x05`

以 `40x24` 的导出为例：

- `0x28` 是宽度 `40`
- `0x18` 是高度 `24`
- `0x05` 是每行字节数 `5`

它们是工具头，不是图像像素。

### 9.2 正式资源中应该怎么处理

正式资源中应写成：

- `width = 40`
- `height = 24`
- `stride = 5`
- `data = 纯像素数组`

而不是把 `0x28, 0x18, 0x05` 也塞进 `data` 里。

### 9.3 `SetDirRev[124]` 这类旧数组是什么

这类数组更像是“已经去掉工具头的纯像素点阵”，例如注释里写明：

- 文本或图标名称
- 尺寸 `62x16`

此时 `124 = 62 * (16 / 8)`，说明它本质上是纯位图 payload。

换句话说：

- `SetDirRev[124]` 这类数组接近正式资源的数据区
- `HeatingImage134[]` 里前 3 个字节则是工具附带的额外元信息

二者差别不在“哪个对哪个错”，而在于一个已经被清洗过，一个还是工具原始导出格式。

## 10. 正式工作流

推荐统一工作流如下：

1. 在 `tools/assets/display/source_bmp/` 保存 BMP 源稿。
2. 在取模工具导出原始数组，归档到 `tools/assets/display/tool_exports/`。
3. 根据导出设置判断资源格式是 `PAGE_VLSB` 还是 `ROW_MSB`。
4. 清洗掉工具冗余头，把元数据转入正式结构体。
5. 将正式资源放入 `applications/resources/fonts/` 或 `applications/resources/images/`。
6. 由 `display_service` 或后续页面模块组合使用。
7. 每次调整后先跑 host test，再构建，再下载验证。

## 11. 当前落地决策

本轮重构正式采用以下原则：

1. 保留 `tools/assets/display/tool_exports/legacy_arrays/ascii_font.c`、`tools/assets/display/tool_exports/legacy_arrays/mod_font.c` 作为历史资产档案，不直接参与当前构建。
2. 在 `components/display/mono_canvas/` 新增正式资源 ABI 与绘制接口。
3. 在 `applications/resources/` 建立正式字体与图片资源目录。
4. 当前显示服务改为使用“图片 + 标题 + 副标题”的组合页面来验证新体系。
5. host test 先验证资源 ABI 和绘制逻辑，再进行整机下载。

## 12. 结论

Themis 最合理的资源方案不是“只保留一张图”或“只留一个字库”，而是建立三层并存的体系：

- `tools/assets/display/` 负责源资产与历史资产
- `components/display/mono_canvas/` 负责统一绘制 ABI
- `applications/resources/` 负责正式运行时资源

这样才能同时满足：

- 设计可追溯
- 资源可复用
- 代码分层清晰
- 后续功能扩展稳定
