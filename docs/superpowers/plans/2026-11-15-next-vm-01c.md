## Proposed minimal implementation after approval

### 1. Runtime lifecycle mailbox

Add to `runtime/include/foc_runtime.h`:

```text
enum foc_runtime_request_result {
    NONE, PENDING, APPLIED, REJECTED, CANCELLED
};

struct foc_runtime_lifecycle_request {
    enum foc_runtime_action action;
    enum foc_runtime_mode requested_mode;
    uint32_t request_sequence;
    uint32_t source_session;
    uint32_t produced_us;
};

struct foc_runtime_lifecycle_result {
    enum foc_runtime_request_result result;
    uint32_t request_sequence;
    uint32_t applied_session;
    uint32_t h0_us;
    enum foc_safe_state state;
    uint32_t faults;
    int pipeline_status;
};
```

Proposed APIs:

```text
foc_runtime_publish_lifecycle_request(runtime, request, now_us)
foc_runtime_read_lifecycle_result(runtime, result)
```

The first API is Foreground-only and returns `BUSY` when the one-entry mailbox
is occupied. H0 copies a request with acquire semantics at its normal H0
boundary and publishes the terminal result with release semantics. A bounded
two-slot record plus atomic slot indices avoids treating a multi-field C struct
as naturally atomic. The producer is single Foreground; the consumer is H0.

H0 ordering would remain:

```text
schedule/deadline check
  -> drain STOP/inhibit
  -> cancel pending request on STOP/fatal fault
  -> validate request session/sequence/time/state
  -> existing foc_runtime_lifecycle()/foc_runtime_set_mode()
  -> ordinary Runtime/Pipeline control
  -> publish APPLIED/REJECTED/CANCELLED result
```

No Foreground path writes `runtime->mode`, Safety state, PI state, or output
state. `START` still requires READY, `SET_MODE` still requires DISABLED and
confirmed INHIBIT, and fault clear never auto-starts.

### 2. Serial Target Policy

Add an immutable initialization policy in the shared Serial Adapter:

```text
FOC_SERIAL_TARGET_LOCKED       // default and Board1 wrapper
FOC_SERIAL_TARGET_VIRTUAL_ONLY // explicit Host simulator injection only
```

`foc_serial_init()` remains a locked Board1 wrapper. A separate explicit Host
initializer injects `VIRTUAL_ONLY`; no UART field, parameter write, HELLO
payload, or client identity can change the policy after initialization.

Board1 behavior remains:

```text
ARM  -> OUTPUT_LOCKED
START -> OUTPUT_LOCKED
UPDATE -> existing Board1 output lock/rejection
```

The Host policy may publish a lifecycle mailbox request, but still cannot write
Safety state or bypass the Runtime H0 and virtual Output Adapter.

### 3. Protocol/runtime service seam

The current `foc_serial_poll()` performs a Foreground poll and a zero-input H0
step internally. That is correct for the Board1 simulator but conflicts with
VM-01b's virtual event scheduler. The minimal approved seam should split frame
consumption/dispatch from the caller-owned Runtime service step, while keeping
the existing COBS, CRC, Session, Sequence, UART buffer, STOP reservation and
response queue logic. Board1 keeps the existing wrapper and service order;
Host Virtual calls the same dispatch through VM-01b's virtual clock.

No new V1 message ID or SET_MODE wire meaning is proposed. Mode selection,
time advance, load schedule and sensor fault schedule remain Host-only scenario
controls. ARM/START/STOP use existing V1 messages.

### 4. Host Virtual executable and CLI

After the seam and mailbox are approved, add a Host-only executable under
`simulation/` that owns `foc_virtual_current`, `foc_serial`, UART buffers and a
virtual clock. Its stdout is binary COBS/CRC protocol bytes only. Diagnostics,
metrics and request-result metadata use stderr or a separate CSV/JSON file.

The Python CLI will gain a same-process virtual workflow entry point. It will
perform HELLO, CAPABILITY_READ, mode scenario selection, ARM, result polling,
START, SETPOINT, virtual-time advance, STATUS/TELEMETRY, STOP and final result
read. A new process is not started for each step. Existing `--simulator`, real
SerialTransport, wire vectors and Board1 lock behavior remain intact.

Because V1 STATUS/TELEMETRY layouts are already fully occupied, Host-only
metadata will explicitly expose `request_accepted`, `request_applied_by_h0`,
`virtual_pwm_update_accepted`, `simulated_current_valid`,
`simulated_sensor_valid`, and `physical_applied=false`. No existing wire field
will be redefined.

## Negative test gate required before implementation is called complete

### Mailbox

- normal ARM/START applied exactly once;
- full mailbox returns BUSY and never overwrites;
- duplicate/old sequence rejected;
- stale source session rejected;
- expired request and half-range timestamp cases rejected;
- pending START cancelled by STOP;
- pending ARM/START cancelled by fatal fault;
- SET_MODE rejected outside DISABLED+confirmed INHIBIT;
- fault clear cannot auto-START;
- result cannot be attributed to the next request;
- producer publication while H0 consumes remains coherent;
- H0 miss/deadline produces a terminal result without blocking.

### Target policy and Board1

- default policy remains LOCKED;
- ARM/START remain OUTPUT_LOCKED on Board1;
- PARAM_WRITE, HELLO and session identity cannot select VIRTUAL_ONLY;
- Board1 UPDATE remains rejected;
- Host policy is reachable only through explicit Host initialization;
- no Host-only object or symbol enters the ARM firmware.

### Virtual device/CLI

- bad CRC, bad session, replay, RX gap, TX busy and truncated frame;
- Host UPDATE rejection and STOP before UPDATE;
- invalid sensor and command timeout;
- stale mode/session command after a mode change;
- simulator exit does not leak a prior session;
- Current, Velocity and Position workflows produce real Runtime/Plant metrics;
- repeated execution yields identical CSV/replay hash.

## Verification and stop conditions

The negative-first mailbox, Board1 policy, Python/C wire, and three virtual CLI
demonstrations passed. The ARM rebuild grew only in the shared Runtime/Serial
code and is documented with `.text/.data/.bss`, Flash/RAM, and hash deltas in
the evidence report. An unexplained ARM delta, any Board1 lock bypass, any stale
request execution, or any P0/P1 race remains a stop condition for follow-up.
