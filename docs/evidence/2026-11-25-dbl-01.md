# DBL-01｜镜像中 double 的使用范围：写入规范并加检查守住

2026-11-25，分支 `codex/falconfoc-v2-vm01a`，基线 `a54c4c8`（TEST-01）。只改规范和检查，固件与 ARM 镜像不变。

## 结论

代码规范第 6 节原来写"镜像代码不用 `double`"，但 ARM 镜像实际链接了 libgcc 的软件双精度库（约 2.4 KiB）。逐处审计的结果：

- double 只出现在 Foreground 的一次性标定估计里，H0/H1 热路径里没有。
- 这些 double 有数值上的理由，不能直接换成 float。
- 处理方式：规范改为明确的例外，再加两道检查守住它：
  - 质量门禁限定允许出现 double 的文件；
  - fwinteg 检查热路径到不了任何软件双精度函数。

## 审计

调用软件双精度函数的位置（LTO 默认镜像，直接调用次数）：

| 函数 | 次数 | 来源 |
| --- | ---: | --- |
| `foc_board_calibration_poll` | 322 | CAL-3/4/7 的 finish 与求解（LTO 内联） |
| `cal_record_estimate` | 117 | CAL-3 记录推送 |
| `foc_board_profile_refresh` | 39 | `foc_motor_pi_design` |
| `foc_motor_id_push` | 38 | 正规方程累加 |
| `cal_coast` | 33 | 滑行检查最小二乘 |
| `foc_calibration_sqrt` 等 | 少量 | double 开方辅助 |

为什么不能直接换成 float：

- CAL-3（`foc_motor_id`）、CAL-4（`foc_flux_id`）、CAL-7（`foc_mechanical_id`）和滑行检查都先累加最小二乘的正规方程，再用展开式 v² − 2θᵀb + θᵀGθ 算残差，并按 `(8n+64)·eps·scale` 估算舍入误差的上界。
- 拟合越好，残差相对 v² 越小，展开式里的项相消越严重。
- 换成 float 后 eps 约为 1.2e-7。几千个样本时，这个误差界约为 v² 的 1e-3，换算成残差 RMS 约为 0.03×v_rms，会超过残差上限，标定会直接判失败。
- 要用 float 就得改算法（回归量居中缩放、增量 QR 或 Givens 分解）。另外 `foc_motor_id.h`、`foc_flux_id.h`、`foc_mechanical_id.h` 的公开结构里有 64 个 double 字段，有 20 多个 Host 文件在用。
- 这一步收益约 2.5–3 KiB ROM。RES-01 之后带存储镜像还有约 15.3 KiB 余量，所以暂不做。

## 改动

- **代码规范第 6 节**：
  - double 的唯一例外：Foreground 里一次性的标定估计（`foc_motor_id`、`foc_flux_id`、`foc_mechanical_id`、`foc_calibration_math`、`foc_board_calibrate` 的滑行检查），并写明原因；
  - 新增 double 必须进白名单并写明原因；
  - 自检清单同步更新。
- **`scripts/gates/check_image_double.py`**（质量门禁调用）：
  - 扫描范围是编入镜像的源文件：`firmware/at32f415/src`、`firmware/at32f415/include`，以及 `falconfoc-board1` 列出的可移植源文件和同名头文件，共 78 个；
  - 比较前先去掉注释和字符串；
  - 白名单外出现 double 判失败；白名单里的文件不再含 double，或已不编入镜像，也判失败，保证名单准确。
- **`arm_static.py` 新增 `no_double_in_hot_path`**：
  - 从反汇编里的直接分支（`bl`、`b.w`、条件分支，含尾调用）建调用图；
  - 起点：每个有独立代码的中断入口，以及 H0 通过函数指针调用的 `cal_adc_tap`、`cal_h0_observer`。`Reset_Handler` 是前台入口（会调用 main），不算起点；
  - 确认这些起点都到不了软件双精度函数（`__aeabi_d*`、`__*df2/3`、各种转换函数、`foc_calibration_sqrt/fmax/fmin`），有就报告最短路径；
  - `ADC1_IRQHandler` 或 `TMR1_CH_IRQHandler` 找不到也判失败。
- firmware README（Flash 预算一节）、scripts README。

## 验证

- **`check_image_double.py`**：当前代码通过（78 个文件，白名单 10 个）。在 `core/src/foc_trig.c` 临时加一行 `static double`，它正确地判失败并报出行号；还原后再次通过。
- **`no_double_in_hot_path`**：
  - TEST-01 的五个 ARM 镜像全部 PASS。起点 9 个：ADC1、CAN1_RX0、SPI1、TMR1_CH、TMR5_GLOBAL、USART1、BusFault，以及 `cal_adc_tap`、`cal_h0_observer`。
  - 用合成反汇编测试：中断经尾调用到达 `__aeabi_dmul`，检查判失败并给出路径。
  - 调试时曾误把 `Reset_Handler` 当作起点，结果找到 `main -> foc_board_calibration_poll -> __adddf3`，说明遍历本身能发现前台里真实存在的 double。
- **fwinteg `run1`**：VERDICT PASS，0 findings；三套工具链各 161 项全部通过。五个镜像的 `no_double_in_hot_path` 都 PASS，fwinteg 内部跑的质量门禁里 `check_image_double.py` 也通过。

## 局限

- 调用图只包含直接分支。经函数指针的间接调用只覆盖了已知的 H0 回调；以后新增在中断里调用的回调，要把它加进 `HOT_CALLBACKS`。
- 源码检查只看 `double` 关键字。float 表达式里的 double 字面量（例如没写 `f` 后缀的 `0.5`）也会引入软件双精度，这一点由 `no_double_in_hot_path` 在热路径上兜底；前台里的这类情况只增加 ROM，不影响时序。
