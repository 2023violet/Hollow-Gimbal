## 3. 实际数据流

### Current

```text
Current command
  -> foc_runtime_publish_command()
  -> H0 ADC decode / Current PI / SVPWM
  -> foc_device_pwm_request
  -> virtual output adapter
  -> accepted UPDATE 才更新 Plant 的零阶保持电压
  -> PMSM Plant
  -> ADC ranks + encoder code
```

### Velocity

```text
Velocity target
  -> foc_runtime_publish_motion_command()
  -> Encoder code -> foc_encoder_update() -> H1
  -> production foc_velocity_step()
  -> Iq reference
  -> H0 Current PI -> SVPWM -> accepted virtual UPDATE
  -> Plant mechanical velocity
```

H0 使用 200 us，H1 使用 500 us；H1 只使用 Encoder 软件链提供的机械速度，不能直接
读取 Plant 的真实速度。H1 target 带有 mode、source sequence、source timestamp 和
`motion_session`，H0 只消费当前 session 的 target。

### Position

```text
Continuous position target
  -> production Position P
  -> velocity reference (limited)
  -> production Velocity PI
  -> Iq reference
  -> H0 Current PI -> SVPWM -> accepted virtual UPDATE
  -> continuous mechanical position -> encoder feedback
```

Plant 保存连续机械角；只有电角度转换使用周期角语义。Position 场景没有直接写回
Plant，也没有绕过速度、电流或 Safety 限制。

## 6. Lifecycle, mode, STOP and fault evidence

The executable S01 sequence is:

```text
CURRENT RUNNING
  -> revoke command / STOP
  -> DISABLED
  -> SET_MODE(VELOCITY), fresh command and H1 target
  -> ARM -> READY
  -> START -> RUNNING, motion_session=2
```

The virtual-current test additionally verifies:

- VELOCITY → POSITION after STOP uses a new session and does not reuse the old velocity target.
- POSITION → CURRENT after STOP uses a new session, accepts a fresh Current command, and
  reaches RUNNING only after ARM and START.
- A mode request is serviced only through the existing H0 `action` path; the test never writes
  `runtime->mode` or Safety state directly.
- Current UPDATE rejection leaves the staged PI transaction uncommitted (VM-01a regression).
- S02 runs a command-timeout branch to `FAULT_LATCHED` (`faults=1`) and a separate sensor
  transport-failure branch with refreshed commands. The sensor branch becomes non-RUNNING and
  accepts no UPDATE after the failure; it does not auto-START. The timeout branch also stays
  fault-latched and cannot be restarted by the old command.

The observed `motion_session` increments across STOP/mode/fault boundaries. H1 target identity
contains the session, and H0 rejects the target when its mode/session no longer matches.

## 8. Lifecycle mailbox design (not implemented)

Production Runtime currently has H0-owned `foc_runtime_fast_input.action` and a restricted
Foreground timeout-clear mechanism, but no general Foreground-to-H0 request mailbox for ARM,
START, or SET_MODE. The next implementation should keep H0 as the only owner of mode, Safety,
and output state.

### Proposed request record

```text
request_type: NONE | ARM | START | SET_MODE | CLEAR_FAULT
target_mode: CURRENT | VELOCITY | POSITION (only for SET_MODE)
request_seq: strictly increasing producer sequence
source_session: producer-visible session identity
published_us: monotonic source timestamp
```

The mailbox should use a bounded single-slot or two-slot release/acquire publication pattern
matching the existing command/sensor slots. Foreground may publish a request and receive
`PENDING`; H0 copies and validates it at its next due H0 event. H0 alone can return:

```text
PENDING -> APPLIED | REJECTED | CANCELLED
```

The observable result must include request sequence, applied session, H0 timestamp, current
state, and rejection reason. `Request Accepted` means only that the record was admitted to the
mailbox. `Request Applied` means H0 completed the state transition. `Actual Output Applied`
requires the output adapter/Safety transaction to acknowledge an UPDATE; it is a separate fact.

Rules for the next implementation:

- Reject duplicate or stale request sequences idempotently; do not re-run a request after H0
  has published a terminal result.
- Reject a request whose source session is stale, whose timestamp is outside the bounded
  freshness window, or whose state precondition is false.
- STOP/inhibit and latched faults have higher priority than normal mailbox requests. A pending
  ARM/START/SET_MODE is cancelled or rejected when H0 observes a stop request or fault.
- A mode change must first establish confirmed inhibition, then increment the motion session;
  new commands and H1 targets must carry the new session before ARM/START can apply.
- Fault clear returns to DISABLED and never performs an implicit ARM or START.
- Foreground must publish with release semantics; H0 must load with acquire semantics. The
  terminal result must be published with release and read with acquire. No Foreground code may
  write `runtime->mode`, Pipeline Safety state, or output ownership directly.
- Use `foc_runtime_request_timeout_clear()` as the reference for cancellation, pending result,
  and H0 validation, but keep lifecycle requests separate from timeout recovery policy.

This is a design artifact only. Implementing it requires a separate authorization and review
because it changes production lifecycle admission and its serial-facing observability.

## 9. Serial Target Policy design (not implemented)

The proposed policy is a target-local capability layer after the shared Protocol/Session
decoder and before Runtime request publication:

```text
Shared Protocol / Session / CRC
             |
        Target Policy
       /             \
Board1: LOCKED     Virtual: HOST_ONLY
             |
        Runtime request mailbox
             |
          Safety Gate
```

Required first version:

- Default policy is `LOCKED`; a missing or unknown target policy never unlocks Board1.
- Board1 keeps `FOC_MSG_ARM` / `FOC_MSG_START -> OUTPUT_LOCKED` and receives no new virtual
  permission or global `ENABLE_PWM` flag.
- Virtual Host operations may exercise software Runtime state and report simulated telemetry,
  but they never imply physical power application.
- Reuse the existing decoder, CRC, session, and sequence semantics; do not create a second
  protocol parser or add UART V1 message types in this stage.
- Keep `virtual_update_accepted` and `simulated_current_valid` distinct from
  `physical_applied`. The latter requires a Board-owned witness that is currently absent.
- STOP/inhibit must bypass ordinary response queue backpressure. A rejected target request must
  be visible as a policy result, while Runtime Safety remains the final output gate.
- Capability reporting must name the target (`BOARD1_LOCKED` or `HOST_VIRTUAL`) so a Host result
  cannot be mistaken for Board1 capability.

This policy is also design-only in VM-01b. No production Serial or Protocol behavior changed.
