# NEXT-VM-01b Virtual Motion Implementation Plan

## Goal

Extend the VM-01a Host virtual motor harness through the production Runtime's
Velocity and Position paths, and exercise lifecycle/session boundaries without
changing Board1, Serial, Protocol, Safety, or production lifecycle APIs.

## Scope and constraints

- Reuse the VM-01a PMSM Plant, ADC/Encoder adapters, output journal, virtual
  clock, and Runtime event ordering.
- Keep H0 at 200 us and H1 at 500 us; publish motion targets through
  `foc_runtime_publish_motion_command()` and consume them through H1/H0.
- Measure tracking and transaction outcomes; mark physically/configuration
  limited cases `EXPECTED_DEGRADED` rather than treating numerical boundedness
  as quality acceptance.
- Design, but do not implement, a Foreground-to-H0 lifecycle request mailbox
  and a default-locked Serial Target Policy.
- Do not enable physical PWM, modify Board1 output lock, alter UART V1, or run
  hardware.

## Tasks

1. Verify VM-01a simulation, Current replay, existing Host/Board/ARM evidence,
   and the unmodified production boundaries.
2. Add motion-facing virtual harness APIs for target publication, mode request,
   sensor-fault injection, motion observations, and saturation counts.
3. Add the deterministic `falconfoc-virtual-motion` executable with V01/V02/
   V03/P01/P02/S01/S02 scenarios and CSV metrics.
4. Add lifecycle/session and fault-isolation assertions without changing
   Runtime implementation.
5. Document the lifecycle mailbox and Serial Target Policy as next-stage
   designs, including request/result state distinctions and STOP/FAULT
   priority.
6. Run simulation, sanitizer, Runtime, Host, source/CMake/format, Scope, and
   ARM regression lanes; record any environment block explicitly.

## Verification criteria

- VM-01a CTest and replay fingerprint remain unchanged.
- Current, Velocity, and Position use real Runtime H1/H0/Current paths and
  accepted output drives the shared Plant.
- All seven motion scenarios run deterministically and report RMSE, tail RMSE,
  peak error, overshoot, settling time, saturation, update counts, state,
  faults, session, and replay fingerprint.
- S01 demonstrates STOP plus a new mode/session and legal re-entry; S02
  demonstrates timeout/sensor failure and no automatic restart from stale data.
- Board1 ARM binary remains byte-identical to the VM-01a/RC0 hash.
- No commit, push, merge, reset, clean, stash, flash, power-up, or motor run.
