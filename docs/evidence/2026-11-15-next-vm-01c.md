## 3. Finding: current Serial service coupling

`firmware/at32f415/src/foc_serial.c:foc_serial_poll()` currently consumes bytes,
dispatches requests, calls Foreground supervision, and the Board1 simulator
calls a zero-input `foc_runtime_h0_step()` after every poll. That coupling is
safe for the existing locked Board1 simulator but cannot be reused verbatim by
VM-01b's virtual scheduler: it would execute an additional H0 step outside the
200 us virtual event sequence.

The approved implementation therefore needs a small service seam that preserves
the existing protocol parser, UART buffer, session, sequence, STOP reservation,
CRC and response behavior while allowing the Host Virtual owner to call Runtime
service at the VM-01b virtual timestamp.

No seam has been added before approval.

## 4. Proposed lifecycle mailbox

The mailbox is a one-producer Foreground / one-consumer H0 bounded request path.
It reuses `FOC_RUNTIME_ACTION_ARM`, `FOC_RUNTIME_ACTION_START`,
`FOC_RUNTIME_ACTION_SET_MODE`, existing `foc_runtime_lifecycle()`,
`foc_runtime_set_mode()`, and existing STOP/Fault Clear behavior.

Request fields:

```text
action, requested_mode, request_sequence, source_session, produced_us
```

Result fields:

```text
NONE, PENDING, APPLIED, REJECTED, CANCELLED
request_sequence, applied_session, h0_us, state, faults, pipeline_status
```

Proposed public APIs:

```text
foc_runtime_publish_lifecycle_request(runtime, request, now_us)
foc_runtime_read_lifecycle_result(runtime, result)
```

Foreground can publish only. H0 is the sole owner allowed to change mode,
Safety, PI state, lifecycle state, or output. A full mailbox returns `BUSY` and
never silently replaces a pending request. A two-slot record plus atomic slot
indices is required; ordinary multi-field structs are not treated as atomic.

Publication uses release semantics and H0 consumption uses acquire semantics.
Terminal result publication is release; result observation is acquire. H0
processes STOP/inhibit and fatal fault before normal lifecycle requests, then
validates state, session, sequence and timestamp before calling the existing
lifecycle implementation.

`ACCEPTED` means only “stored in the mailbox”. `APPLIED` means H0 completed the
software transition. Neither means physical PWM output was applied.

## 5. Proposed Serial Target Policy

The policy is immutable after initialization:

```text
FOC_SERIAL_TARGET_LOCKED
FOC_SERIAL_TARGET_VIRTUAL_ONLY
```

`foc_serial_init()` remains the Board1 locked wrapper. Only an explicit Host
Virtual initializer can inject `VIRTUAL_ONLY`. No UART message, parameter write,
HELLO field, session value or client self-identification can change policy.

Board1 remains:

```text
ARM    -> OUTPUT_LOCKED
START  -> OUTPUT_LOCKED
UPDATE -> existing Board1 output lock/rejection
```

Host Virtual may publish a lifecycle request into the mailbox but must still pass
H0 Runtime/Safety and the virtual Output Adapter. No global `ENABLE_PWM`, no
second protocol parser, and no V1 message or field change is proposed.

Existing V1 STATUS/TELEMETRY payloads are fully occupied. Therefore request
result identity and virtual-only fields must be Host metadata (JSON/CSV or a
diagnostic channel), not a redefinition of existing wire fields:

```json
{
  "request_accepted": true,
  "request_applied_by_h0": true,
  "virtual_pwm_update_accepted": true,
  "simulated_current_valid": true,
  "simulated_sensor_valid": true,
  "physical_applied": false
}
```

All values must come from the actual mailbox, Runtime snapshot, virtual Output
Adapter or Plant; no idealized success flags are allowed.

## 8. Implemented lifecycle mailbox

`runtime/include/foc_runtime.h` and `runtime/src/foc_runtime.c` now contain a
bounded two-slot request/result protocol. A Foreground producer claims the
idle state, writes the complete request, then publishes `PUBLISHED` with
release semantics. H0 claims with acquire semantics, copies the inactive slot,
and publishes the complete result to the alternate result slot before releasing
the mailbox back to idle. A result read uses acquire semantics and never treats
the multi-field record as naturally atomic.

Requests carry:

```text
action, requested_mode, request_sequence, source_session, produced_us
```

Results carry:

```text
NONE, PENDING, APPLIED, REJECTED, CANCELLED
request_sequence, applied_session, h0_us, state, faults, pipeline_status
```

The full mailbox returns `FOC_RUNTIME_ERR_BUSY`. Duplicate/old sequences,
expired timestamps, and stale source sessions are rejected before enqueue. H0
consumes requests only at its normal due boundary. STOP/fatal fault cancellation
is handled before normal lifecycle control; fault recovery and an in-flight
clear cancel a queued lifecycle request. Existing `foc_runtime_lifecycle()` and
`foc_runtime_set_mode()` remain the only state transition implementations.

The new `test-foc-runtime-mailbox` is negative-first and covers normal apply,
full mailbox, duplicate/old sequence, STOP cancellation, stale session,
expired request, and SET_MODE identity. Runtime CTest now contains `11/11` tests
and Simulation CTest contains `14/14`.

## 9. Implemented Serial Target Policy

`foc_serial_init()` still initializes `FOC_SERIAL_TARGET_LOCKED`. A separate

The Board Host serial test now covers explicit Host policy with STOP cancellation
and confirms that it does not create physical output permission. Existing Board1
tests continue to assert the default lock and output rejection.

## 10. Host Virtual Serial device and CLI

`simulation/src/falconfoc_virtual_device.c` owns one VM-01b virtual current
context, the production `foc_serial` adapter, UART byte buffer, and a virtual
clock. It reuses the C COBS/CRC/Session/Sequence implementation. stdout contains
only binary V1 bytes; stderr contains `FALCONF0C_META` JSON metadata.

The process accepts `--mode current|velocity|position` and `--advance-us` as
Host-only controls. Mode selection is applied through the Runtime mailbox before
the first V1 request. ARM, START, SETPOINT and STOP still travel as existing V1
messages. The Python `virtual-demo` keeps one simulator process alive and runs:

```text
HELLO -> CAPABILITY_READ -> SETPOINT -> ARM -> SETPOINT refresh -> START
       -> repeated SETPOINT/TELEMETRY -> STOP -> STATUS -> TELEMETRY
```

The refresh before START is required by the existing Runtime command-freshness
contract. No new wire message or SET_MODE wire meaning was added.

The actual commands used were:

```powershell
python tools/falconfoc-cli/falconfoc_cli.py --simulator build/vm01a-simulation/falconfoc-virtual-device.exe virtual-demo --virtual-scenario current --advance-us 500
python tools/falconfoc-cli/falconfoc_cli.py --simulator build/vm01a-simulation/falconfoc-virtual-device.exe virtual-demo --virtual-scenario velocity --advance-us 500
python tools/falconfoc-cli/falconfoc_cli.py --simulator build/vm01a-simulation/falconfoc-virtual-device.exe virtual-demo --virtual-scenario position --advance-us 500
```

All three runs produced `ACCEPTED` V1 ARM/START responses, `APPLIED` mailbox
results for ARM and START, `RUNNING` virtual telemetry with accepted UPDATEs,
and final STOP/STATUS state `DISABLED`. The Current, Velocity and Position runs
reported `physical_applied=false` throughout. The Host metadata exposed actual
virtual UPDATE counts and mechanical position/velocity; it did not rewrite V1
STATUS/TELEMETRY.

The dedicated Python test passed `5/5` with
`FOC_SERIAL_SIM=build/sw04-host/foc-serial-sim.exe` and
`FOC_VIRTUAL_DEVICE=build/vm01a-simulation/falconfoc-virtual-device.exe`. It
asserts both lifecycle `APPLIED` results, nonzero virtual UPDATEs, final STOP,
and `physical_applied=false`.
